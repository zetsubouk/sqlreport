# SQL 报表工具 — 增量 PRD（v0.2）

作者：产品经理 许清楚 ｜ 状态：待架构师评审 ｜ 基线：v0.1（PLAN.md）

> 本文档为**增量 PRD**，只描述三条新需求的变更部分，不重复 v0.1 既有功能。
> 延续既有边界（不做）：拖拽设计器 / 多级表头 / 套打 / 用户体系 / 登录。

---

## 1. 项目信息

- **Language**：中文
- **Programming Language**：Python 3（延续标准库 http.server 路线，沿用现有单文件 + JSON 配置架构）
- **Project Name**：sqlreport v0.2
- **原始需求复述**：
  1. 在 Web 界面管理数据库连接（增删改查数据源、连接测试），替代手改 `datasources.json`；
  2. 支持跨多数据源（如 MySQL 与 SQLServer）的联合查询，多库数据关联/合并出一张报表；
  3. 大数据量查询优化与缓存机制，提升稳定性，需给出候选方案与取舍建议。

## 2. 使用者画像

| 角色 | 画像 | 核心诉求 |
|------|------|----------|
| 管理员 | K 本人/开发者，懂 SQL 与数据库连接参数 | 界面上快速配好数据源并验证连通，不再 SSH 改 JSON 重启 |
| 业务用户 | 只读报表的使用者，不懂 SQL | 打开 `/r/<id>` 填条件出数、导 Excel，响应速度不能太慢 |

权限模型延续现状：配置管理（数据源管理页）仅限管理员；业务用户继续免登录只读 `/r/<id>`。**不引入用户体系**——数据源管理页的保护方式（如简单口令/仅内网/代理层控制）为待确认问题。

## 3. 产品目标

1. **配置自助化**：管理员在 Web 界面 3 分钟内完成一个数据源的创建、测试与启用，全程无需改文件、重启服务。
2. **跨库出数**：业务用户在一张报表里看到来自 ≥2 个不同数据库的关联/合并数据，使用方式与单库报表无差别（填参数 → 出表格 → 导 Excel）。
3. **大数据量稳定**：百万行级明细查询不拖垮服务，重复查询响应显著加快，失败/超时有明确提示而非页面挂死。

## 4. 用户故事

**数据源管理（R1）**
- 作为管理员，我想在 Web 界面新增/编辑数据源（类型、host、port、库名、账号、密码），这样不必登服务器改 JSON。
- 作为管理员，我想在保存前点「测试连接」看到成功/失败与耗时，这样交付现场能当场排查连通问题。
- 作为管理员，我想禁用（隐藏）某个数据源而不删除它，这样引用它的报表不报错，且隐藏模板（`_` 前缀）语义得以保留。
- 作为管理员，我想看到每个数据源当前被哪些报表引用，这样删除前不会误伤线上报表。

**跨源联合查询（R2）**
- 作为报表作者（管理员），我想在报表里定义多个取数步骤（各连各的库、各写各的 SQL），并把前序结果按列关联或纵向合并，这样 MySQL 的订单数据能和 SQLServer 的客户主数据拼进一张表。
- 作为业务用户，我照常填参数、点查询，不感知数据来自几个库，这样使用门槛不变。

**大数据量（R3）**
- 作为业务用户，我查询百万行明细时页面给出进度/截断提示，而不是一直转圈或 502。
- 作为业务用户，我第二次打开同一张常用报表（参数相同）时秒出结果，这样日常看数体验流畅。
- 作为管理员，我想控制缓存开关与有效期，这样实时性要求高的报表不走旧数据。

## 5. 需求池（P0 / P1 / P2）

### R1 系统设置 — 数据源管理

| 优先级 | 需求 | 说明与验收标准 |
|--------|------|----------------|
| P0 | 数据源 CRUD 页面 | `/datasources` 列表页 + 新建/编辑表单（类型 MySQL/SQLServer/SQLite、连接参数、备注）；保存写回 `datasources.json`（或迁移到新配置文件，架构师定）；改动**免重启生效** |
| P0 | 连接测试 | 表单内「测试连接」按钮，返回 成功（含耗时 ms）/失败（含错误摘要）；不真正执行业务 SQL，仅建连 |
| P0 | 密码处理 | 密码在列表页打码显示；保存时兼容"留空=不修改"；延续 P0-3 的 gitignore 约定，界面写回的文件同样不入库 |
| P1 | 引用检查 | 列表页展示每个数据源被哪些报表引用；删除被引用数据源时二次确认 |
| P1 | 启用/禁用开关 | 等价于现有 `_` 前缀隐藏语义的界面化操作 |

### R2 跨数据源联合查询

| 优先级 | 需求 | 说明与验收标准 |
|--------|------|----------------|
| P0 | 多步骤取数（数据集） | 报表 JSON 支持定义多个数据集：`"datasets": [{"name":"a", "ds":"mysql1", "sql":"..."}, ...]`，各数据集独立走各自数据源，参数占位符 `{{}}` 规则沿用；兼容现有单 SQL 报表（旧格式自动视为单数据集） |
| P0 | 纵向合并（union） | 同构数据集上下拼接为一张结果表（列对齐按列名，缺失列留空）——实现成本低，业务最常用（如各分店库汇总） |
| P1 | 横向关联（join/lookup） | 以主数据集为左表，按指定键列关联次要数据集（类似 VLOOKUP / left join），支持一对一取值即可，不做全功能 join；大数据集关联的性能边界由架构师评估 |
| P1 | 编辑器支持 | 报表编辑器可增删数据集、为每个数据集单独选数据源与 SQL；导出 Excel 对合并后的最终结果表生效 |
| P2 | 数据集预览 | 编辑器里单数据集试运行（前 N 行），便于分步排查 SQL |

### R3 大数据量查询优化与缓存

用户明确要求"采用什么方案"。以下为**候选方案与取舍建议**，最终选型留给架构师评审。

**3a. 查询优化候选方案**

| 方案 | 取舍建议 |
|------|----------|
| A. SQL 层分页（LIMIT/OFFSET、OFFSET/FETCH，服务端翻页） | 效果最确定，但需要报表定义分页参数、前端改翻页交互，改动面较大。建议：P1，先做「默认 max_rows 截断 + 明确提示」（v0.1 已规划），翻页视真实痛点再上 |
| B. 行数硬上限 + 超时（每数据源 timeout，超限截断） | 成本极低、防拖垮效果立竿见影。建议：**P0 必做**（即 PLAN.md 的 P2-1 前置），是稳定性底线 |
| C. 只读账号 + SQL 白名单校验（仅 SELECT/WITH、禁多语句） | 延续 PLAN.md 既定方案。建议：P0（与 B 同批） |

**3b. 缓存候选方案**

| 方案 | 取舍建议 |
|------|----------|
| A. 进程内 TTL 缓存（dict，key=报表id+参数值哈希，TTL 可配） | 零依赖、~50 行代码，契合单进程标准库架构；重启失效、无持久化。建议：**P0/P1 首选**，报表 JSON 增加 `"cache_ttl": 300`（0=不缓存） |
| B. SQLite 文件缓存（缓存落盘到 cache.db） | 可持久化、重启不失效，但引入缓存失效管理复杂度。建议：仅当用户反馈"重启频繁丢缓存"再做（P2） |
| C. 数据库侧物化/汇总表（DBA 建视图或定时汇总） | 不改本工具代码，效果最好，但依赖客户 DBA 配合。建议：写进部署文档作为推荐实践，工具不实现 |

**优先级汇总**

| 优先级 | 需求 |
|--------|------|
| P0 | 行数硬上限 + 查询超时 + 只读 SQL 校验（方案 B+C，稳定性底线） |
| P0 | 查询中/超时/超限的用户提示（loading 态、明确错误文案，不再页面挂死） |
| P1 | 进程内 TTL 缓存（方案 A），报表级 `cache_ttl` 配置 |
| P1 | SQL 层分页/服务端翻页（方案 A，视痛点排期） |
| P2 | SQLite 落盘缓存（方案 B） |

### 明确不做（本版边界）

- 不做：拖拽报表设计器、多级表头、套打、用户体系/登录（沿用 URL 免登录 + 代理层兜底）
- 不做：全功能跨库 SQL 引擎（不做跨库真 join 下推、分布式事务）；跨源只做"多步取数 + Python 侧合并"
- 不做：数据同步/ETL、定时任务、消息队列等重型组件——保持零/低依赖单进程形态
- 不做：缓存与外部系统（Redis 等）集成

## 6. 技术规范（移交架构师的取舍点）

1. **配置存储**：数据源继续存 `datasources.json` 还是迁移 `config/datasources.json` + 原子写入（临时文件 + rename）？写并发如何保护？
2. **免重启生效**：数据源懒加载缓存如何失效（mtime 检测 / 手动刷新）？
3. **跨源合并内存模型**：union/join 在 Python 侧全量载入的行数上限与内存预算；join 用 dict 哈希还是逐行查找？
4. **缓存 key 设计**：参数序列化规则、TTL 到期刷新策略、编辑报表后是否主动失效（建议：保存报表即清该报表缓存）。
5. **数据集兼容**：`datasets` 数组与现有单 `sql` 字段的双格式兼容策略。
6. **数据源管理页的访问保护**：免登录前提下如何防止业务用户改配置（仅本机访问 / 简单口令 / 代理层路径控制）？
7. **单文件膨胀**：预计新增 ~200-300 行，是否提前触发 PLAN.md 的 800 行拆模块阈值。

## 7. Open Questions（待用户/架构师确认）

1. 跨源需求中，业务上更多是**纵向合并**（多个同类库汇总）还是**横向关联**（维表补列）？影响 P0 是否必须含 join。
2. 典型"大数据"规模是多少行？（10 万 / 百万 / 千万）——决定分页是否必须进 P0。
3. 报表实时性要求：缓存 5 分钟是否可接受？是否存在必须实时的报表？
4. 数据源管理是否需要操作留痕（谁在何时改了连接）？（无用户体系下只能记 IP，价值有限，默认不做）
